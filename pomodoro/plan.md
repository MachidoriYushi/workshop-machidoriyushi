# ポモドーロタイマー Web アプリ 実装計画

## 目的

この計画は、`architecture.md` と `features.md` に基づき、Go の `net/http`、HTML、CSS、JavaScript を使ってポモドーロタイマー Web アプリを実装する手順を定義する。

要望に合わせ、実装はテストから進める。最初に期待する振る舞いをテストとして固定し、その後に最小限の実装を追加してテストを通す。

## 実装方針

- テストを先に追加し、失敗を確認してから実装する。
- Go サーバーは画面と静的ファイルの配信に集中させる。
- タイマー状態、進捗、統計、通知は JavaScript 側で管理する。
- 初期実装ではバックエンド API とデータベースは追加しない。
- 設定と統計は `localStorage` に保存する。
- UI は添付モックを基準に、中央カード、円形進捗、操作ボタン、今日の進捗パネルを実装する。

## 実装対象

- 25 分の作業タイマー
- 5 分の休憩タイマー
- 開始、一時停止、再開、リセット
- 作業と休憩のモード切り替え
- 円形の進捗表示
- 今日の完了数と集中時間の統計表示
- ブラウザ通知
- サウンド通知
- レスポンシブ Web UI
- 設定と統計の保存

## フェーズ 1: Go サーバーのテストを作る

### 目的

Web アプリを配信する最小サーバーの契約を先に固定する。

### 先に作るテスト

`internal/server/handlers_test.go` を追加し、以下を確認する。

- `GET /` が `200 OK` を返すこと。
- `GET /` のレスポンスに `ポモドーロタイマー` が含まれること。
- `GET /healthz` が `200 OK` を返すこと。
- `GET /healthz` のレスポンスが `ok` であること。
- 存在しないパスが `404 Not Found` を返すこと。

### 実装内容

- `internal/server` パッケージを追加する。
- `NewMux` または `NewServer` を実装する。
- `/`、`/healthz`、`/static/*` のルーティングを登録する。
- `main.go` からサーバーを起動する。

### 完了条件

- `go test ./...` が成功する。
- ブラウザで `/` にアクセスできる。

### 実装内容

### 完了条件

## フェーズ 3: タイマー状態遷移のテストを作る

### 目的

UI 実装の前に、タイマーの状態遷移と条件を JavaScript の純粋なロジックとして固定する。

### 先に作るテスト

`web/static/js/timer.test.js` を追加し、以下を確認する。

- 初期状態が `work`、`idle`、`1500` 秒であること。
- `START` で `idle` から `running` になること。
- `PAUSE` で `running` から `paused` になり、残り時間が保持されること。
- `RESUME` で `paused` から `running` になること。
- `RESET` で `idle` に戻り、残り時間が初期値に戻ること。
- `COMPLETE` で `completed` になり、残り時間が 0 になること。
- 完了処理が同一セッションで 2 回実行されないこと。
- 作業完了後の次モードが `break` になること。
- 休憩完了後の次モードが `work` になること。

### 実装内容

- `timer.js` に状態生成関数を実装する。
- イベントを受け取り次状態を返す reducer 相当の関数を実装する。
- DOM 操作に依存しない関数として、状態遷移をテスト可能にする。

### 完了条件

- JavaScript の状態遷移テストが成功する。
- 共通不変条件を満たさない状態が作られない。

## フェーズ 4: 進捗計算と時刻計算のテストを作る

### 目的

ブラウザの `setInterval` 遅延に左右されにくいタイマー計算を実装する。

### 先に作るテスト

- `durationSeconds = 1500`、`remainingSeconds = 1500` のとき進捗が 0% であること。
- `remainingSeconds = 750` のとき進捗が 50% であること。
- `remainingSeconds = 0` のとき進捗が 100% であること。
- 進捗率が 0% 未満にならないこと。
- 進捗率が 100% を超えないこと。
- 経過時間が duration を超えた場合、残り時間が 0 になること。

### 実装内容

- `calculateRemainingSeconds` を実装する。
- `calculateProgressPercent` を実装する。
- `Date.now()` 相当の現在時刻を引数で受け取れる設計にし、テストで時刻を固定できるようにする。

### 完了条件

- 時刻計算と進捗計算のテストが成功する。
- タブ非アクティブ時の遅延を前提にしても破綻しない。

## フェーズ 5: 統計更新のテストを作る

### 目的

完了したセッションだけを統計に反映することを保証する。

### 先に作るテスト

- 作業セッション完了時に `completedWorkSessions` が 1 増えること。
- 作業セッション完了時に `totalFocusSeconds` が 1500 増えること。
- 休憩セッション完了時に `completedBreakSessions` が 1 増えること。
- 休憩セッション完了時に `totalBreakSeconds` が 300 増えること。
- `PAUSE` では統計が増えないこと。
- `RESET` では統計が増えないこと。
- 同じ完了セッションが二重に加算されないこと。

### 実装内容

- 統計の初期状態を作る関数を実装する。
- 完了イベントから統計を更新する関数を実装する。
- 今日の統計を日付単位で扱うための判定関数を実装する。

### 完了条件

- 統計更新テストが成功する。
- リセットや一時停止による誤加算が起きない。

## フェーズ 6: 保存と復元のテストを作る

### 目的

設定と統計を `localStorage` に保存し、再読み込み後に復元できるようにする。

### 先に作るテスト

- 設定を JSON として保存できること。
- 統計を JSON として保存できること。
- 保存済み設定を復元できること。
- 保存済み統計を復元できること。
- 不正な保存値の場合は既定値にフォールバックすること。
- `localStorage` が使えない場合でもメモリ上の状態で動作できること。

### 実装内容

- 保存用キーを定義する。
- `saveState`、`loadState`、`saveStats`、`loadStats` を実装する。
- JSON parse エラーや型不一致に対するフォールバックを実装する。

### 完了条件

- 保存と復元のテストが成功する。
- 不正な保存値でアプリが起動不能にならない。

## フェーズ 8: 通知機能を実装する

### 目的

タイマー完了時にブラウザ通知とサウンド通知を行う。

### 先に作るテストまたは確認観点

- 通知権限が `granted` の場合だけブラウザ通知を試行すること。
- 通知権限が `denied` の場合は画面内表示にフォールバックすること。
- サウンド通知が無効の場合は音を鳴らさないこと。
- サウンド再生に失敗しても完了処理が維持されること。

### 実装内容

- 通知許可を要求する処理を実装する。
- 完了時のブラウザ通知を実装する。
- Web Audio API または音声ファイルによるサウンド通知を実装する。
- 通知失敗時の画面内メッセージを実装する。

### 完了条件

- 完了時に通知が試行される。
- 通知に失敗してもタイマー状態と統計が壊れない。

## テスト追加の優先順位

1. Go の HTTP ハンドラテスト。
2. JavaScript の状態遷移テスト。
3. JavaScript の時刻計算と進捗計算テスト。
4. JavaScript の統計更新テスト。
5. JavaScript の保存と復元テスト。
6. 通知処理のフォールバック確認。
7. ブラウザでのレスポンシブ UI 確認。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| `setInterval` が遅延して残り時間がずれる | 現在時刻との差分で残り時間を計算する |
| 完了処理が複数回実行される | `status` と `completedAt` で完了済み判定を行う |
| リセットや一時停止で統計が増える | 統計更新を `COMPLETE` のみに限定する |
| 通知権限が拒否される | 画面内通知へフォールバックする |
| サウンド再生がブロックされる | ユーザー操作後に初期化し、失敗しても処理を継続する |
| `localStorage` の値が壊れる | 型検証し、不正値は既定値へフォールバックする |
| モバイルで UI が崩れる | 固定幅を避け、最大幅とレスポンシブ制約を使う |

## 最初に着手するタスク

最初の実装タスクは、Go サーバーのテスト作成から始める。

1. `internal/server/handlers_test.go` を作成する。
2. `/`、`/healthz`、存在しないパスの期待値をテストに書く。
3. `go test ./...` が失敗することを確認する。
4. `internal/server` と `main.go` を実装してテストを通す。

この順番により、配信基盤を先に安定させてから、HTML、CSS、JavaScript の実装に進む。
